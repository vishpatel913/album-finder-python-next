# Adopting Alembic (migrations) — step-by-step

Goal: evolve the DB schema **without nuking**, preserving your data. After this,
the loop is: change a model → generate a migration → apply it. Data persists.

Each stage has a **✓ Check** — don't move on until it passes.

Two facts about this setup that matter throughout:
- The `api` service **bind-mounts `./backend` → `/app`**, so `alembic.ini`,
  `migrations/`, `entrypoint.sh` etc. are live in the container — no rebuild to
  change them.
- The venv is an **anonymous volume** (`/app/.venv`). Adding a *dependency*
  (alembic) means rebuilding the image **and** refreshing that volume with
  `-V`, which keeps your `pgdata` (only anonymous volumes are renewed).

Commands assume you run from the repo root. We use `docker compose exec api …`
(runs in the live container) rather than `run`, to avoid venv-volume surprises.

---

## Stage 1 — Add the dependency

Edit `backend/pyproject.toml`, add to `dependencies`:

```toml
    "alembic (>=1.14.0,<2.0.0)",
```

Rebuild the image and refresh the venv volume (keeps your data):

```bash
docker compose up -d --build -V api
```

> `-V` (`--renew-anon-volumes`) recreates the `/app/.venv` anon volume from the
> freshly built image. Named volumes like `pgdata` are untouched — your data stays.

**✓ Check:** alembic is now in the container.
```bash
docker compose exec api alembic --version      # prints e.g. "alembic 1.14.x"
docker compose exec database psql -U postgres -d music_library -c "SELECT count(*) FROM album;"
```
The count should still show your existing rows (proves the rebuild kept data).

## Stage 2 — Scaffold the config

Create these four files (the bind mount makes them live immediately — no rebuild).

**`backend/alembic.ini`**
```ini
[alembic]
script_location = migrations
prepend_sys_path = .
# sqlalchemy.url is injected from $DATABASE_URL in env.py — do not set it here.
```

**`backend/migrations/env.py`**
```python
import os

from alembic import context
from sqlalchemy import engine_from_config, pool
from sqlmodel import SQLModel

# Import every model so its table registers on SQLModel.metadata.
# Autogenerate diffs THIS metadata against the database.
from domain.artist.model import Artist  # noqa: F401
from domain.album.model import Album  # noqa: F401
from domain.track.model import Track  # noqa: F401

config = context.config

# Runtime DB URL wins over anything in alembic.ini.
db_url = os.getenv("DATABASE_URL")
if db_url:
    config.set_main_option("sqlalchemy.url", db_url)

target_metadata = SQLModel.metadata


def run_migrations_offline() -> None:
    context.configure(
        url=config.get_main_option("sqlalchemy.url"),
        target_metadata=target_metadata,
        literal_binds=True,
        compare_type=True,
    )
    with context.begin_transaction():
        context.run_migrations()


def run_migrations_online() -> None:
    connectable = engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    with connectable.connect() as connection:
        context.configure(
            connection=connection,
            target_metadata=target_metadata,
            compare_type=True,  # detect column type / nullability changes
        )
        with context.begin_transaction():
            context.run_migrations()


if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()
```

**`backend/migrations/script.py.mako`** — note the `import sqlmodel` line; SQLModel
autogenerated migrations reference its types, so they won't import without it.
```mako
"""${message}

Revision ID: ${up_revision}
Revises: ${down_revision | comma,n}
Create Date: ${create_date}
"""
from typing import Sequence, Union

from alembic import op
import sqlalchemy as sa
import sqlmodel
${imports if imports else ""}

revision: str = ${repr(up_revision)}
down_revision: Union[str, None] = ${repr(down_revision)}
branch_labels: Union[str, Sequence[str], None] = ${repr(branch_labels)}
depends_on: Union[str, Sequence[str], None] = ${repr(depends_on)}


def upgrade() -> None:
    ${upgrades if upgrades else "pass"}


def downgrade() -> None:
    ${downgrades if downgrades else "pass"}
```

**`backend/migrations/versions/.gitkeep`** — empty file so the folder is tracked.

**✓ Check:** env.py imports cleanly and can reach the DB.
```bash
docker compose exec api alembic current
```
Expect **no output** (no revision yet) and **no traceback**. A traceback here
means an import path or DB-connection problem — fix before continuing.

## Stage 3 — Generate the baseline migration

The baseline must contain "create all tables" so a fresh DB can be built from
it. We autogenerate it by diffing the models against an **empty scratch DB**
(your real DB already has the tables, so diffing against it would produce nothing).

```bash
# 1. empty scratch DB in the same Postgres
docker compose exec database createdb -U postgres alembic_tmp

# 2. autogenerate by pointing alembic at the empty scratch DB
docker compose exec -e DATABASE_URL=postgresql://postgres:postgres@database:5432/alembic_tmp \
  api alembic revision --autogenerate -m "baseline schema"

# 3. drop the scratch DB
docker compose exec database dropdb -U postgres alembic_tmp
```

**✓ Check:** a new file exists under `backend/migrations/versions/`. Open it and
confirm `upgrade()` has `op.create_table("artist" / "album" / "track", …)` with:
- `album.year` and `album.genre` **nullable=True**
- foreign keys `album.artist_id → artist.id`, `track.artist_id → artist.id`, `track.album_id → album.id`

This file is your schema's starting point — commit it.

## Stage 4 — Mark your existing DB as "already at baseline" (preserve data)

Your real DB already has these tables, so we **stamp** it (record the version
without running `create_table`). First make the existing table actually match
the baseline (your earlier nullability change), so future autogenerates don't
flag a spurious diff:

```bash
docker compose exec database psql -U postgres -d music_library -c \
 "ALTER TABLE album ALTER COLUMN year DROP NOT NULL;
  ALTER TABLE album ALTER COLUMN genre DROP NOT NULL;"

docker compose exec api alembic stamp head
```

**✓ Check:**
```bash
docker compose exec api alembic current     # prints the baseline revision id
docker compose exec database psql -U postgres -d music_library -c "SELECT count(*) FROM album;"
```
Revision id shown, data still present. Alembic now considers your DB up to date.

## Stage 5 — Wire it into the app

**`backend/entrypoint.sh`** — replace the table-creation line:
```sh
# was: python -m scripts.init_db
alembic upgrade head
```
(Leave the seed line and the `exec uvicorn …` line as they are. `scripts/init_db.py`
is now legacy — migrations own the schema.)

**`Makefile`** — add targets:
```makefile
.PHONY: migration
migration: ## Generate a migration from model changes:  make migration m="add x"
	docker compose exec api alembic revision --autogenerate -m "$(m)"

.PHONY: migrate
migrate: ## Apply all pending migrations
	docker compose exec api alembic upgrade head

.PHONY: downgrade
downgrade: ## Roll back the last migration
	docker compose exec api alembic downgrade -1
```

**✓ Check:** restart and confirm the app boots via alembic, data intact.
```bash
docker compose up -d            # entrypoint now runs `alembic upgrade head`
docker compose logs api | tail -n 20     # should show alembic running, no errors
```
Already at head, so it's a no-op; the API starts and your rows are still there.

## Stage 6 — Test the real loop (a schema change, no nuke)

Make a throwaway change to prove evolution works. E.g. in
`backend/domain/album/model.py` add a nullable column:
```python
    rating: int | None = None
```
Then:
```bash
make migration m="add album.rating"
# open the new file in backend/migrations/versions/ — confirm it has
#   op.add_column("album", sa.Column("rating", sa.Integer(), nullable=True))
make migrate
```

**✓ Check:** column added, data preserved.
```bash
docker compose exec database psql -U postgres -d music_library -c "\d album"
docker compose exec database psql -U postgres -d music_library -c "SELECT count(*) FROM album;"
```
`rating` appears; row count unchanged.

To undo the experiment: `make downgrade`, then remove the column from the model
and delete that version file (or keep it — your call).

---

## Stage 7 — (Optional, once) Prove the fresh-install path

This **does** wipe data, so only when you're happy — it confirms a clean clone
builds the schema purely from migrations:
```bash
make nuke && make up     # empty DB -> entrypoint runs `alembic upgrade head` -> tables built
make seed                # repopulate from your Library.xml
```
**✓ Check:** tables exist and seed succeeds with no `create_all` anywhere. From
here on, schema changes are migrations — **you never nuke to change the schema again.**

---

## Daily workflow from now on

```
edit a model
make migration m="what changed"     # review the generated file!
make migrate                        # applied; data preserved
```

## Gotchas
- **Always eyeball the generated migration.** Autogenerate is good, not perfect
  (renames look like drop+add; some constraint changes need hand-editing).
- **New dependency** (not just a schema change) → `docker compose up -d --build -V api`
  again (rebuild + refresh venv volume), as in Stage 1.
- If `alembic current`/commands can't import `domain…`, check `prepend_sys_path = .`
  in `alembic.ini` and that you're running inside `/app` (the default WORKDIR).
